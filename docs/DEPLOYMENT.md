# Deployment Guide

## Recommended architecture

The deployable complete application lives in `万卷浮生_Web应用/`. It serves the native browser client, REST API, and WebSocket endpoint from one Express process and stores state in SQLite.

For the first public preview, deploy it as one Render Web Service with one persistent disk:

```text
Browser ── HTTPS / WSS ──> Express + WebSocket ──> SQLite persistent disk
                              │
                              └──> Optional third-party LLM APIs
```

This keeps API calls and WebSocket connections same-origin. GitHub Pages is not suitable for the complete app because it cannot run Node.js, SQLite, or WebSocket services. A split Vercel/Render deployment is possible, but adds CORS and two deployment lifecycles without improving the first preview.

The repository root includes [`render.yaml`](../render.yaml), using Render's documented `rootDir`, `buildCommand`, `startCommand`, generated secret, and persistent-disk fields.

## Before deploying

Run the same local checks as CI:

```bash
cd frontend
npm ci
npm run lint
npm run build

cd ../万卷浮生_Web应用
npm ci
node --check server.js
node --check auth.js
node --check ws-server.js
```

Do not commit `.env` files or real API keys.

## Deploy with Render Blueprint

1. Merge the reviewed OSS-readiness branch into `main`.
2. In Render, choose **New > Blueprint** and connect `fengjiehzi/floating-scrolls`.
3. Select the repository-root `render.yaml` and review the proposed Web Service and 1 GB persistent disk.
4. Confirm that `JWT_SECRET` is generated by Render. Never replace it with the placeholder from `.env.example`.
5. Add only the AI provider credentials you intend to use, such as `OPENAI_API_KEY` or `DEEPSEEK_API_KEY`, through Render's Environment settings.
6. Deploy and wait for the `/api/characters` health check to pass.

Persistent disks and service plans can affect cost. Review the current Render plan before confirming the Blueprint.

## Environment variables

| Variable | Production value |
| --- | --- |
| `NODE_ENV` | `production` |
| `HOST` | `0.0.0.0` |
| `PORT` | Provided automatically by Render; do not hard-code it in the dashboard |
| `JWT_SECRET` | Strong generated secret; required |
| `DB_PATH` | `/var/data/floating-scrolls.db` when using the included disk |
| `CORS_ORIGIN` | Leave unset for same-origin deployment; set to comma-separated HTTPS origins only for a separate frontend |
| `AI_PROVIDER`, `AI_MODEL` | Optional defaults |
| Provider `*_API_KEY` | Optional; set only for providers used by the deployment |

The server and WebSocket endpoint share the same port. The native client derives `ws:` or `wss:` from `window.location`, so an HTTPS Render URL automatically uses secure WebSocket (`wss:`) without a hard-coded hostname.

## CORS

Production defaults to same-origin requests. If the React client is later hosted on another domain, set `CORS_ORIGIN` to that exact origin, for example `https://example.vercel.app`. Multiple origins can be comma-separated. Do not use `*` for an authenticated public deployment.

The React client reads `VITE_API_BASE_URL` at build time. For split deployment, create an untracked `frontend/.env.production` containing the HTTPS API origin, then rebuild. The current React battle flow does not yet provide the complete authenticated WebSocket client, so the same-origin native client remains the recommended full demo.

## Post-deploy smoke test

Replace the URL with the real Render URL:

```bash
curl --fail https://YOUR-SERVICE.onrender.com/
curl --fail https://YOUR-SERVICE.onrender.com/api/characters
curl --fail https://YOUR-SERVICE.onrender.com/api/items
curl --fail https://YOUR-SERVICE.onrender.com/api/ai/providers
```

Then verify in a browser:

1. Home page loads without fatal console errors.
2. A user can register and sign in.
3. Character and item catalogs load.
4. The battle lobby establishes a `wss:` connection after authentication.
5. AI provider checks fail gracefully when no API key is configured and succeed for the configured provider.

## Operational notes

- Keep a single application instance while using SQLite; multiple instances would not share one attached disk.
- Back up `/var/data/floating-scrolls.db` before destructive schema or content changes.
- Rotate `JWT_SECRET` or provider keys immediately if they are exposed. Rotating `JWT_SECRET` invalidates existing sessions.
- Monitor WebSocket disconnects and service restarts during the preview period.
